# Reproducible duplicate audit and partitions

H02 consumes the accepted H01 `preparation.json` at the pinned revision. The pinned preparation SHA-256 and size must match `docs/data/h01-evidence.json`; source settings, source-manifest reference, permanent provenance/notices, four pinned Parquet assets, and all nine derived-file sizes/hashes authenticate before an article index is read. Missing pinned preparation fails and requires separate H01 preparation/acceptance; H02 never silently reconstructs it. Partial/stale H01 output fails authentication. Synthetic bootstrap preparation remains explicit and can create its own H01 fixture reconstruction.

`python -m ralup prepare-data --config configs/data.json` runs the narrow, non-scoring source-only bootstrap through H02. It returns a content-addressed manifest path and SHA, `status=incomplete`, and exit 1 because H03–H08 are pending. This does not pass WP02 or authorize model scoring. `prepare_corpus(config: ResolvedConfig)` is the separate F01 research entry. It revalidates the full F01 snapshot for `purpose=prepare-data`, checks pinned source identity, and authenticates dependency-lock/environment plus passing WP00 evidence. No future WP02 or unresolved training settings are prerequisites. Its H01 locator is the project-root `configs/data.json`, whose output is `data/processed/wikitext/<pinned-revision>/provenance/preparation.json`; call from the project root. The manifest records the exact preparation/source references, source-only config hash, and resolved-config hash when used. Bootstrap explicitly records a null resolved-config hash and its narrower authorization.

Document identity is split plus article ordinal. A raw content SHA is a duplicate identity and can belong to multiple independently protected documents. Article metadata preserves global split row ranges, compact row-index file/byte ranges, source shard order, preamble identity, and unchanged content offsets. Original rows/separator flags remain in authenticated `<QQB` indexes; no inline source strings or duplicate corpus byte copies are added.

The audit order is raw exact grouping/overlap, 128-MinHash candidates (16 bands of 8), exact Jaccard verification, connected components, protected-component exclusion and canonical raw hash choice, then raw partition hashing. All protected documents remain intact, including duplicates. A protected node anywhere in a component excludes every training node. Otherwise, retain the training document with lexicographically smallest raw content SHA; identical-SHA ties use stable document ID. Every exact group, near candidate, full-tuple intersection/union/similarity, acceptance, component, retained/excluded hash and exclusion reason is recorded.

Only the duplicate audit decodes UTF-8 and applies NFKC, lowercase, then whitespace splitting. A document shorter than 13 tokens contributes its complete token tuple, including the empty tuple. Other documents contribute sets of consecutive 13-token tuples. Raw content and partition hashes never normalize bytes. Exact candidate verification uses full token tuples, so shingle-hash or signature collisions cannot become similarity matches.

Stable candidate definitions, also recorded in each manifest:

- Seed bytes are ASCII `ralup-minhash-v1`, hex `72616c75702d6d696e686173682d7631`. Function indices are uint32 little-endian `0..127`. SHA-256 of seed plus index gives `a = uint64_le(digest[:8]) | 1` and `b = uint64_le(digest[8:16])`.
- A shingle hash is the first uint64 little-endian of SHA-256 over ASCII `ralup-shingle-v1` plus concatenated UTF-8 tokens, each framed with its uint32 little-endian byte length. An empty tuple has empty framed payload. For each function use `(a*x+b) mod 2**64`; odd multiplication makes this a 64-bit bijection. Take the minimum over the document's shingles.
- A band key comprises the band ordinal and eight consecutive minima serialized uint64 little-endian. No Python `hash()` or process-randomized seed is used. Signature arithmetic processes at most 4,096 shingles × 128 functions per chunk. Only one document's tokens remain in signature generation; exact verification materializes only its candidate pair's full tuple sets.
- Affine permutations, finite 64-bit shingle hashes and LSH are candidate heuristics. Candidate misses remain possible, including at Jaccard .8; standard ideal-independent MinHash detection formulas do not establish completeness for these affine functions. Exact acceptance uses integer `5*intersection >= 4*union`. No complete absence of public-data contamination is claimed.

Partition hashing is the first uint64 big-endian of `SHA256(b"ralup-split-v1" + raw_article_bytes)`. Meta-train uses `5*x < 2**64`; otherwise meta-development uses `4*x < 2**64`; otherwise target-training. This exactly implements `[0,.20)`, `[.20,.25)`, `[.25,1)` without floating-point thresholds. Each partition records actual document IDs, hashes, counts and bytes. Allocation adequacy must be assessed before modeling; an amendment invalidates dependent artifacts. The measured H02 allocations are in `h02-evidence.json`; no model-learning sufficiency claim follows from counts alone.
