# E2M1 conversion and F03 evidence

The project uses 15 unique numerical values: `[-6,-4,-3,-2,-1.5,-1,-.5,0,.5,1,1.5,2,3,4,6]`. A returned uint8 **ordinal** indexes this numerically sorted set and supports directional adjacency. The canonical encoding nibbles, in the same order, are `[15,14,13,12,11,10,9,0,1,2,3,4,5,6,7]`. Neither ordinal parity nor numeric sign determines the tie rule: nearest ties select the even least-significant **significand** bit. For example, `-5` selects `-4` (ordinal 1, nibble `1110`) rather than `-6` (ordinal 0, nibble `1111`). Nibble 8 represents negative zero in OCP; this project canonicalizes numerical zero to ordinal 7 and nibble 0.

## Primary source and project choices

The [official OCP Microscaling Formats v1.0 specification](https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf), version table dated 7 September 2023, was browser-inspected on 3 October 2026, particularly printed pages 8 and 11–13. E2M1 uses `S EE M`, exponent bias 1, signed zeros, subnormal magnitudes .5, and normal magnitudes through 6; no NaN/Inf encoding exists. [Encoding and midpoint reference](e2m1-encoding-reference.json) preserves all 16 nibbles and all 14 numerical midpoint choices. [Authored inspection notes](ocp-inspection-notes.txt) retain the factual inspection evidence.

Direct raw PDF retrieval returned Cloudflare HTTP403 for four official variants. [Source status](ocp-source.json) records `raw_pdf_sha256: null` and `raw_pdf_bytes_saved: false`; the inspection-notes SHA256 is **not a PDF hash**. This unresolved source-artifact checksum is retained explicitly. No PDF checksum is inferred or fabricated.

Nearest significand-even rounding and finite saturation follow the declared E2M1 conversion. Positive-zero canonicalization, rejecting original NaN/Inf, and requiring positive finite scales are stricter **project choices**. OCP permits wider-format infinities to saturate and leaves NaN conversion implementation-defined; it also allows other rounding modes. Simulated row-scaled W4A32 does not claim full MXFP4 compliance: OCP MXFP4 additionally uses blocks of 32 and E8M0 scales.

## Coordinate and storage contract

`e2m1_oracle(x, scale)` converts real inputs/scales to CPU float64, rounds in `x/scale` coordinates by comparing all 15 distances, then multiplies the selected numerical level by scale. Clipping scaled coordinates to the finite endpoints before comparing distances preserves saturation and prevents meaningless overflow of distance arithmetic. It canonicalizes all output zero positive.

`quantize_e2m1(x, scale)` requires FP32 tensors on the same device. It uses direct FP32 division for ordinary normal operands. For any subnormal operand it decodes the original FP32 bit patterns into integer significands/exponents, divides exactly representable significands in normal FP32 range and applies an exact normal power-of-two shift, preserving the rounded coordinate without denormal arithmetic. Exponent differences outside ±28 can only lie inside the zero cell or beyond saturation for every finite significand, so bounded shifts preserve code selection. It then uses 14 sequential exact-threshold comparisons, with each threshold's equality direction determined by significand parity. Working storage is O(P); there is no parameter-by-codebook allocation. Production functions never copy input/output tensors to CPU and never call the CPU oracle. Validation checks integer dtype views of the original bits, including mathematical positivity of subnormal scales. Scalar boolean reductions raise errors synchronously and select the exceptional path; these reductions synchronize the device. No higher-precision production tensor is introduced. Quantization is detached; F04 owns the explicit surrogate backward graph.

A finite original input can overflow its scaled division and still saturates normally. If the selected level multiplied by scale is unrepresentable in the storage dtype, both implementations raise `ValueError` with `reconstruction overflow` instead of emitting Inf or changing the rounded E2M1 level. At subnormal scales or the lowest normal scale exponent, reconstruction multiplies the scale significand by twice the chosen E2M1 magnitude in int32 (at most 28 bits), then assembles the FP32 bits. Normal results use one nearest-even integer-to-FP32 conversion; subnormal results round the exact integer product divided by two directly, including halfway-to-even cases. Bit-based zero canonicalization preserves nonzero subnormal outputs. Float64 storage has the same overflow guard in the oracle. Generic broadcasting applies; callers supply row scales as `[rows,1]`. `directional_neighbor` returns immediate ordinals and a feasibility mask. Direction signs are decoded from their bits so tiny nonzero subnormal directions remain feasible. Zero direction and outward endpoint direction are infeasible and retain the original ordinal.

FP32 division and exact float64 division of FP32 operands can select different codes near ties. For FP32 `x=.175`, `scale=.1`, exact float64 division is about `1.7499999441` and selects 1.5; FP32 division is exactly 1.75 and selects 2. Its negative mirror follows the same encoding rule. This is a coordinate-roundoff effect, not a significand-parity disagreement. The diagnostic reports each such case, its exact and rounded coordinates, both ordinals/physical values, distance to the tie, and one FP32 ULP.

## Predeclared acceptance and actual measurements

F03 freezes exact-case absolute error and code mismatch allowance at zero. For FP32-coordinate reconstructed values only, the relative bound is `2 * finfo(float32).eps = 2.384185791015625e-7`, with absolute bound zero. An exact-scale code mismatch is accepted only when rounded FP32 division lands exactly on a midpoint, the exact coordinate lies within one FP32 ULP, and the selected ordinals are adjacent. Such differences remain in the report and are not hidden by a loose physical-value tolerance. These are F03 format bounds; F05 must freeze its own assistance/mechanism tolerances using this evidence.

CPU and actual MPS (fallback disabled, Python 3.14.6, PyTorch 2.14.1, NumPy 2.5.3, arm64) measured:

| Cohort | Entries | Code mismatches | Maximum physical-value error |
|---|---:|---:|---:|
| All fixed points, ties, adjacent FP32 values, signed zeros, saturation; five exact power-of-two scales | 305 | 0 | 0 |
| Non-power-of-two scales against oracle in rounded FP32 coordinates | 168 | 0 | 2.384185791015625e-7 |
| Same inputs against exact float64-scale coordinates | 168 | 8, all explained | 0.10000000149011612 |
| Seeded 64×1024 tensor against FP32-coordinate oracle | 65,536 | 0 | 1.1920928955078125e-7 |
| Finite original inputs with scaled-division overflow | 2 | 0 | 0 |
| Mixed subnormal/normal operands, lowest scale exponent, underflow ties; exact rounded-storage bits | 4,096 | 0 | 0 (bit-exact FP32 storage) |

All 45 direction/code pairs matched ordinal adjacency and feasibility. All eight device invalid-input/storage-overflow cases were rejected. The MPS check explicitly verifies that values, ordinals and feasibility tensors remain on MPS. Diagnostic copies to CPU occur after production calls solely for independent comparisons.

[Evidence manifest](f03-evidence.json) records hashes for CPU, actual MPS and the separately blocked sandbox MPS report. Exact float64 midpoint neighbors are exercised by unit tests; MPS never uses float64 tensors. Timing in the diagnostic includes input transfer and is a single check timing, not a performance claim or sustained benchmark. The first review exposed MPS flush-to-zero failures for positive subnormal scales and subnormal inputs; fix-round-one evidence supersedes that subset of the original implementation. Six dedicated scale bit patterns (1,3,5,half-min-normal,max-subnormal,min-normal), explicit signed underflow halfway results, tiny directions and the mixed 4,096-case cohort now match CPU ordinals and reconstructed FP32 bits on actual MPS. Full model/optimizer behavior remains unmeasured. F04 adds fit/context/rotation/surrogate checks; F05 adds the complete mechanism gate. No training, dataset access or protected scoring occurred in F03.
