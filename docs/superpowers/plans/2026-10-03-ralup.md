# RALUP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build and evaluate a reproducible M3 Max research system for the conditional RALUP quality claim, allowing positive, negative, inconclusive, and blocked outcomes.

**Architecture:** One Python package shares data, quantization, model, scoring, state and accounting across methods. Four stage plans expose testable interfaces and gate expensive experiments behind numerical, fidelity and development evidence. The controller freezes at deployment; protected scoring is the final one-way stage.

**Tech Stack:** Stable compatible arm64 Python/PyTorch with MPS FP32; NumPy float64 oracle; SciPy numerical integration/statistics; pinned Parquet reader and download tools; pytest; standard-library JSON/hashing/atomic I/O. Resolve versions on the actual machine.

**Spec:** [RALUP design, S01–S39](../specs/2026-10-03-ralup-design.md). Read it and the relevant stage plan before implementation; this handoff requires no originating conversation.

## Global Constraints

- Vocabulary is 257: raw bytes `0..255` and input-only boundary token `256`.
- Context length 256; target blocks contain at most 128 bytes.
- Logical batch initially contains exactly 8,192 scored bytes.
- Quantize internal projections only; all other parameters, arithmetic, gradients, shadows and optimizer state remain FP32.
- Moments remain in original W coordinates.
- Official validation is development; official test stays protected until the locked manifest and all planned final checkpoints exist.
- Two-sided 97.5% paired intervals for each of two co-primary comparisons; both upper bounds must be below zero for H1+H2.
- Null evidence-dependent settings block production execution. Synthetic smoke configurations are separate artifacts.
- Every method uses the same logical byte schedule and common scorer. Additional passes and offline training are charged.
- No product code, dependency installation, data download or experiment has been performed as part of writing these plans. Every command below is a future implementation/verification instruction.

## Review Focus

- A Unicode/empty-row/header ambiguity must preserve exact source bytes and article boundaries — H01/H02.
- A partial block, epoch boundary or interrupted update must retain each selected byte's original context and cursor — H03/H07.
- A backend-dependent boundary margin must reject unsafe assistance without breaking identity or hiding scale refresh — F03–F05/M08.
- An unsupported baseline operation or additional pass must remain visible in claim eligibility and cost — F02/M02–M06/M10/E01.
- A stale manifest, missing arm or divergent seed must prevent a misleading protected result — E02–E04/E07.

## Verification and task completion convention

Each task follows write assertion → observe intended failure → implement → run focused verification → record/commit. A missing-module import can establish the first red state of a new module; numerical tests must also demonstrate rejection of an intentionally wrong behavior (wrong tie, duplicate target, stale history, etc.). Test fixture helpers named in task examples are local fixtures to create in that task, not presumed existing dependencies.

Use `python -m pytest <explicit task files> -q`. Expected pass means exit zero and all task assertions pass; MPS-only checks may skip on CPU, but the MPS gate remains blocked until run on target hardware. Do not turn a skip into a passed experiment gate. After a stage passes, run that stage's specified integration command and record hashes in `progress.json`. Broaden tests only for changed interfaces, failures or unresolved risks.

Quantization and paired comparisons justify numerical/property tests. Documentation and simple reversible scaffolding need only syntax/link/config checks, not tests mirroring their text. Obtain stable CPU fixtures before MPS parity. No neural accuracy claim follows from fixture success.

In test examples, `exact_cpu_state_hash` means a canonical hash of scientific tensors/state, named RNGs, cursor/schedule and deterministic work counters. Exclude elapsed times, run IDs, process metadata and artifact paths from equality, while retaining them in the ledger. Identity-policy tests compare the shared backbone state and independently verify extra policy histories; same-method resume tests include every scientific history. Fixture helpers must implement this explicit distinction.
